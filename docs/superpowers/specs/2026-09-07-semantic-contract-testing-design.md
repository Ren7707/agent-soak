# 语义契约测试设计

日期：2026-09-07

## 1. 背景与目标

当前框架已经能够执行场景、处理重试和超时、登记并清理测试资源，
但“场景执行成功”不等于“产品功能正确”。最典型的问题是：表单中的
“设备平台”实际表示操作系统平台，测试却填入 `test computer 0001`，
接口返回成功并创建设备，测试框架因此误判功能正常。

本阶段的目标是让框架发现真实使用场景中的业务缺陷，尤其是以下类型：

- 输入格式正确但业务语义错误；
- 前端表达的业务规则与后端实际接受范围不一致；
- 请求成功但资源状态、页面回显或后续操作不符合用户意图；
- 字段之间、实体之间或生命周期之间违反业务不变量；
- 同义值、大小写、空白和重复提交导致数据不一致。

框架不追求完全自动猜测所有业务规则。大模型负责从源码、接口和页面
生成候选规则与测试计划；框架核心使用确定性断言、运行时观测和证据链
做最终判定。

## 2. 非目标

本阶段不实现以下能力：

- 无授权地访问生产环境或绕过写入安全门；
- 让大模型直接修改被测产品源码；
- 让模型单独决定测试通过或确认缺陷；
- 对任意网站进行零配置、无限制的全自动爬取；
- 用单一领域的特殊规则替代通用契约模型；
- 在没有证据的情况下把语义猜测报告为确定缺陷。

## 3. 核心概念

### 3.1 SemanticProfile

描述实体字段的业务语义，而不只是字符串、数字等技术类型。

```json
{
  "entity": "device",
  "field": "platform",
  "semantic_type": "operating_system_platform",
  "description": "设备运行的系统平台类型",
  "examples": ["windows", "macos", "linux", "custom_os"],
  "negative_examples": ["test computer 0001", "办公室设备"],
  "policy": {
    "allowed_values": "known_or_explicit_custom",
    "reject_unclassified_value": true,
    "normalize_case": true,
    "trim_whitespace": true
  },
  "evidence_refs": ["evidence-001", "evidence-002"]
}
```

语义画像必须区分：

- 字段的技术类型；
- 字段在用户任务中的含义；
- 合法值的类别或枚举；
- 邻近但错误的语义类别；
- 是否允许自定义值；
- 规范化和唯一性策略；
- 与其他字段、实体和状态的关系。

### 3.2 SemanticSample

描述一个针对语义规则生成的输入样本。样本至少包含值、样本类别、
生成理由和关联规则。

通用样本类别包括：

- `valid`: 同类合法值；
- `boundary`: 同类边界值；
- `nearby_semantic`: 邻近但不同语义类别的值；
- `wrong_type`: 明显不属于该字段的值；
- `missing`: 缺失字段或空值；
- `normalization`: 大小写、空白、同义词和 Unicode 变体；
- `duplicate`: 重复提交或重复资源；
- `relationship`: 与其他字段或实体关系冲突的值。

### 3.3 BusinessInvariant

描述操作完成后必须保持的业务事实。例如：

- 非法语义值不得创建资源；
- 结束时间不得早于开始时间；
- 已删除资源不得继续被详情接口返回；
- 用户只能修改自己有权限访问的项目；
- 规范化后相同的标识不得产生重复资源；
- 状态为已发布时必须存在可访问的发布版本。

### 3.4 EvidenceBundle

保存规则来源和运行证据，使结果可以复核和重放。证据包括：

- 源码文件、位置和摘要；
- OpenAPI、DTO、校验器或错误码；
- 页面标签、选项、帮助文本和控件类型；
- 实际请求、响应和状态码；
- 页面回显或刷新后的状态；
- 资源创建、详情、列表和删除结果；
- 脱敏后的复现命令和测试输入。

### 3.5 DefectFinding

统一描述质量结论，包括缺陷分类、严重性、置信度、规则来源、样本、
观测结果和证据引用。

## 4. 规则来源与冲突

规则来源按可信度分层，但不是简单覆盖关系：低优先级运行证据可以证明
高优先级规则在实际系统中没有生效。

建议优先级：

```text
显式 Adapter 规则
> 后端 schema / 校验器
> OpenAPI / 接口契约
> 前端类型、控件和文案
> 运行时观测
> 模型语义推断
> 通用风险假设
```

每条候选规则必须绑定来源证据。来源冲突必须保留，不得静默选择一方。
典型冲突如下：

```text
前端只提供 Windows、macOS、Linux
后端接受任意字符串
数据库保存任意字符串
运行时使用“办公室设备”成功注册
```

如果产品没有明确允许自定义系统名称，则该结果可判定为：

```text
semantic_contract_mismatch
semantic_constraint_missing
```

如果产品明确允许任意自定义平台名称，则不能直接判定为缺陷，应该报告
`semantic_boundary_ambiguous`，要求产品规则明确命名、校验或展示策略。

## 5. 模型参与边界

大模型可以执行：

- 从前端、后端、接口文档和页面理解实体与字段；
- 识别字段之间的关系和生命周期状态；
- 生成 SemanticProfile、BusinessInvariant 候选；
- 生成邻近语义样本和测试步骤；
- 解释规则来源与样本分类；
- 根据证据提出缺陷分类和修复建议。

大模型不能执行：

- 直接将自然语言结论写成未经校验的执行计划；
- 直接决定最终通过、失败或确认缺陷；
- 绕过只读模式、写入授权或资源清理；
- 访问未被 Manifest 或用户授权的环境；
- 删除未由当前运行登记的资源。

模型输出必须经过以下流程：

```text
模型输出
  -> JSON Schema 校验
  -> 证据引用校验
  -> 规则冲突检测
  -> 风险等级与执行策略
  -> 确定性测试计划
  -> Adapter 执行
  -> 断言与状态检查
```

缺少证据的模型推断只能产生 `semantic_suspect` 或 `inconclusive`，
不能产生 `confirmed_bug`。

## 6. 测试生成与执行

测试生成围绕实体、字段、操作和状态转换进行，而不是围绕页面按钮数量
进行。每个测试计划必须明确：

- 前置状态；
- 输入样本；
- 操作步骤；
- 预期响应或页面结果；
- 预期资源状态；
- 清理动作；
- 证据采集点；
- 允许的环境异常和不可判定条件。

以设备注册为例，框架应该同时生成：

```text
合法同类值：Windows、macOS、Linux、CustomOS
同类边界值：Windows 11、Custom Linux Distribution
邻近语义值：test computer 0001、office workstation、build server
明显异类值：2026-09-07、user@example.com、123456
规范化变体：windows、 Windows 、WINDOWS
重复场景：相同设备标识重复注册
关系场景：平台与设备类型、架构或代理版本不匹配
```

“test computer 0001”不是格式非法，而是设备名称语义被填入操作系统
平台字段。只有在证据表明字段确实代表系统平台、产品未声明允许任意
自定义名称、且该值被接受并持久化时，才报告确诊缺陷。

执行器需要支持以下确定性断言：

- 响应成功或失败；
- HTTP 状态码和业务错误码；
- 响应字段类型、值和关系；
- 资源是否创建、更新或删除；
- 详情、列表、搜索和刷新后的状态一致性；
- 页面展示与接口状态一致；
- 清理结果和残留扫描结果。

## 7. 通用真实场景风险库

框架内置风险模板，但模板只负责提出测试，不替代产品规则：

### 7.1 语义类别风险

- 设备平台与设备名称混用；
- 邮箱与用户名混用；
- 项目、设备、版本和资源 ID 混用；
- 状态值被填入描述文本；
- 金额、数量、比例和日期的语义混用。

### 7.2 角色与权限风险

- 普通用户执行管理员操作；
- 用户、组织、项目和资源归属错位；
- 被撤销权限的会话继续写入；
- UI 隐藏入口但 API 仍接受操作。

### 7.3 生命周期风险

- 已删除、禁用、归档资源仍可被引用；
- 草稿被当作已发布；
- 已完成任务可被错误重复提交；
- 失败操作产生部分资源或不可见残留。

### 7.4 关系与范围风险

- 开始时间晚于结束时间；
- 子资源归属错误父资源；
- 数量超过库存或配额；
- 区域、时区、币种和地址不一致；
- 设备平台、架构、代理版本之间不匹配。

### 7.5 规范化与幂等风险

- 大小写或前后空格造成重复值；
- 同义值未归一化；
- 重试导致重复创建；
- 删除、更新和提交接口不具备预期幂等性。

### 7.6 成功响应伪象

- HTTP 2xx 但响应体包含错误；
- 返回资源 ID 但详情不可查；
- 页面显示成功但刷新后状态未改变；
- 列表和详情对同一资源给出不同状态；
- 前端显示已应用筛选但结果未变化。

## 8. 结论分类

统一使用以下分类：

- `passed`
- `failed`
- `confirmed_bug`
- `semantic_constraint_missing`
- `semantic_contract_mismatch`
- `normalization_inconsistency`
- `state_transition_violation`
- `unexpected_acceptance`
- `unexpected_rejection`
- `semantic_suspect`
- `inconclusive`
- `environment_error`

严重性建议：

- `high`：非法语义值创建核心资源、权限越界、状态不可逆错误或数据残留；
- `medium`：规则不一致、重复数据、错误状态展示或可恢复业务错误；
- `low`：提示文案、轻微规范化问题或不影响数据正确性的体验问题；
- `unknown`：证据不足，必须人工确认。

## 9. 模块边界

后续实现按以下边界组织：

```text
src/knowledge/   源码、接口、页面和运行观测的采集与脱敏
src/contracts/   规则模型、Schema、冲突合并和确定性断言
src/generators/  语义样本、边界样本、状态与关系场景生成
src/evidence/    证据归档、脱敏、复现信息和报告引用
```

Adapter 继续负责平台动作和平台专用生命周期，但可以额外提供：

```js
{
  contracts,
  discover,
  observe,
  scenarios,
  deleteResource,
  scanResidue
}
```

框架核心不导入具体平台实现。所有写入场景仍然受现有 Manifest、CLI 和
环境变量双重授权约束。

## 10. 验收标准

第一阶段至少需要满足：

1. 可以用结构化契约描述字段语义、允许值、邻近语义和业务不变量。
2. 可以生成并执行 `nearby_semantic`、规范化、重复和关系类测试。
3. 可以检查响应、资源状态、页面回显和清理结果，而非只检查操作完成。
4. 对设备平台注册 `test computer 0001` 的案例，在证据充分时输出
   `confirmed_bug` 或 `semantic_constraint_missing`。
5. 当产品明确允许自定义平台名称时，输出边界不明确或通过，不误报缺陷。
6. 规则、样本、观测和结论都能在报告中追溯到来源和复现命令。
7. 没有写入授权、环境不可用或证据不足时，不产生确定性业务缺陷结论。
8. 现有只读、写入授权、超时、重试、清理和报告测试继续通过。

## 11. 分阶段实现

### 阶段一：确定性契约与变体测试

- 建立契约和证据数据模型；
- 增加语义样本生成器；
- 增加响应、资源和状态断言；
- 增加业务缺陷报告；
- 用本地 Demo 建立语义错误回归测试。

### 阶段二：源码与运行时规则发现

- 扫描前端控件、类型、校验器和 API；
- 生成带证据的候选契约；
- 处理规则冲突和不确定性；
- 增加模型适配接口，但模型输出必须 Schema 校验。

### 阶段三：Skill 化部署

- 根据授权源码生成或更新 Adapter；
- 生成测试计划与候选契约；
- 执行只读探索，再请求写入授权；
- 聚合缺陷、证据和修复建议；
- 保存规则、Adapter 和测试报告版本，支持复用。
